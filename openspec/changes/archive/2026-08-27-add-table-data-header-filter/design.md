## Context

表对象 Data 页已经通过 `loadTableData` → `selectTableData(database, table)` → `executeOnTab` 拉预览行。生成的 SQL 只有 `SELECT * FROM db.table`，行数上限走执行接口的 `rowLimit`（默认 1000）。`ResultGrid` 与 SQL 结果页共用：排序、底栏「过滤已返回结果」、右键列筛选都是对**已返回行**做客户端处理。列头高度写死 30px，选区命中按单行表头计算。

这套模型看前 1000 行够用，按字段把库里的行找出来不够用。本变更只改表 Data 预览查询的生成与网格表头，不改执行/导出 API，不换表格库。

## Goals / Non-Goals

**Goals:**

- 仅在表 Data 列头下显示每列一个筛选框；回车用当前各列草稿重查库。
- 表 Data 上改排序（类型标记循环或右键升序/降序/取消）同样重查，SQL 同时带当前 `WHERE` 与当前单列 `ORDER BY`。
- 刷新按钮重跑「当前筛选 + 当前排序」，不是打回无条件 `SELECT *`。
- 标识符继续用引擎 `identifierQuote`；筛选值用安全字面量，禁止把用户输入拼进 SQL 裸文本。
- SQL 结果页保持客户端筛排，不出现表头筛选行，不改写用户 SQL。
- 筛选解析与 SQL 拼装可单测，不依赖完整页面挂载。

**Non-Goals:**

- 不实现输入即查 / debounce 自动重查；失焦不触发查询。
- 不复刻 dbgate 完整语言（单框 AND/OR、粘贴变 IN、关联表、字典下拉）。
- 不把排序/筛选下推到 SQL 结果页。
- 不新增后端 API、参数化查询协议或 `NULLS FIRST/LAST`。
- 不在表 Data 上做单元格编辑。
- 不把筛选/排序写入 Session Storage 草稿。

## Decisions

### 1. 筛选与排序状态放在表对象 tab，网格受控

`ResultGrid` 现在把 `filter` / `columnFilters` / `sort` 放在组件内部，新结果到来时 `resetView()` 会清空。若筛选框也放在网格里，回车重查后输入会被抹掉。

表对象 tab 持有：

- 每列筛选草稿（按列 `name`，不是视觉下标，避免固定列重排对不上）
- 已应用的解析结果（或与草稿相同，回车时再解析）
- 当前单列排序 `{ column, dir } | null`

`ResultGrid` 在表 Data 模式下：

- 显示表头筛选行，草稿由 props 传入，输入时 `update:filters`
- Enter 发 `apply-query`，不在网格内执行 SQL
- 排序改为受控：点类型标记/右键排序发 `update:sort`，由父级重查
- **不再**对表 Data 做客户端列筛选和客户端排序；行顺序就是这次查询返回的顺序
- 底栏「过滤已返回结果」和右键「筛选」子菜单在表 Data 上隐藏，避免和查库筛选两套语义叠在一起
- 固定列、列宽、选区、值面板、CSV 导出仍是网格本地状态；新结果仍清空选区

SQL 结果页不传筛选行开关（默认关闭），行为与现在一致。

备选是网格内自己拼 SQL 并调用执行。查询绑定、权限、历史、`rowLimit` 都在 `SqlEditorPage` / `executeOnTab` 上，分叉会重复这套路径，因此不采用。

### 2. 一条预览 SQL：`SELECT *` + 可选 `WHERE` + 可选 `ORDER BY`

扩展 `selectTableData`（或并列的 builder），而不是另开表数据 API。Limit 继续留在执行请求的 `rowLimit`，不写进 SQL。空筛选省略 `WHERE`，空排序省略 `ORDER BY`，初次打开与现在相同。

```
SELECT *
FROM "sales"."order_item"
WHERE "status" LIKE '%FAILED%' ESCAPE '\' AND "amount" > 100
ORDER BY "created_at" DESC
```

多列筛选用 `AND`。排序仍是现有单列循环：升序 → 降序 → 取消。列名与 schema/表名一样走 `quoteIdentifier`。

刷新、筛选回车、改排序，三条入口都调用同一 builder + `executeOnTab`。

备选是每次把完整 SQL 丢进隐藏编辑器再执行。表 tab 的 `sql` 目前为空，不应被预览语句污染，也不应出现在可保存脚本里。

### 3. 回车提交全部草稿；改排序立即重查

筛选没有「每个字母查一次」。某一列回车时，用**所有列当前输入框**解析并重查，不是只提交那一列。清空某框再回车表示该列不再参与 `WHERE`。

点排序没有回车手势，因此改排序立即重查（带上当前已应用的筛选）。若某列草稿尚未回车，排序重查使用**上次已应用**的筛选，不把未提交草稿偷偷下推，避免「点一下排序却按半成品条件查库」。筛选回车则把草稿变成已应用条件。

解析失败（如数字列 `>abc`）时不发执行，在该筛选框上显示错误，其它列不受影响。

### 4. 第一期语法：前缀运算符 + 按列类型的默认匹配

解析在纯函数中完成，输入为草稿字符串 + `columnTypeKind(jdbcType)`。

| 输入（trim 后） | 行为 |
|---|---|
| 空 | 该列不参与 |
| `NULL` / `NOT NULL`（大小写不敏感） | `IS NULL` / `IS NOT NULL` |
| 以 `>=` `<=` `<>` `!=` `=` `>` `<` 开头 | 显式比较，右侧为值 |
| 其余裸文本 | 字符串/其它：`LIKE %值%`（值内 `%` `_` `\` 先转义）；数字/日期/布尔：等值 |

约束：

- 数字值必须是十进制数字（可选正负号和小数），否则校验失败，不执行。
- 日期/时间按字面量加单引号交给数据库转换。
- 布尔只接受 `true` / `false` / `1` / `0`（大小写不敏感）。
- 二进制列只允许空、`NULL`、`NOT NULL`。
- 字符串比较与 `LIKE` 使用单引号字面量，引号自身加倍；禁止拼接未转义用户文本。
- 不在第一期做逗号 `IN`、`AND`/`OR` 组合词、正则。

备选是把框内容当原始 SQL 片段。注入面太大，且和现有「前端生成安全预览 SQL」不一致。

### 5. 表头筛选行计入 sticky header，不参与选列

筛选行与列头一起横向滚动，固定列的筛选框与该列同样 sticky。命中测试把 header 高度改为「列头 + 筛选行」；落在筛选行上的 pointer 不是 `header` 选列，输入框 `@pointerdown.stop`，避免打字变成拖选列。

SQL 结果页不渲染筛选行，`HEADER_HEIGHT` 保持 30，现有选区测试不用改预期。

### 6. 历史记录沿用现有预览执行

表 Data 初次打开和刷新已经走 `executeOnTab`，会进当前用户 SQL 历史。筛选/排序重查同样如此，不单开 `source`、也不在本变更里让预览免写历史。若以后历史被预览刷屏，另开 change。

## Risks / Trade-offs

- [每次回车/改排序都是一次正式执行，历史里会出现多条 `SELECT * ... WHERE`] → 与现有刷新行为一致；本变更不改历史策略。
- [LIKE 默认包含会让无索引的大表变慢] → 仍受 `rowLimit` 与现有超时约束；用户可用 `=` 做等值。
- [日期等值 `created_at = '2026-01-01'` 在 timestamp 列上可能匹配不到当天范围] → 第一期接受数据库默认转换；范围查询用 `>=` / `<`。
- [未提交的筛选草稿在点排序时不会生效] → 在筛选框 placeholder/提示里说明回车应用；避免半成品条件误查。
- [表头变高后选区命中算错] → 筛选行高度进入 layout；单测覆盖「点筛选框不选列、点列头仍选列」。
- [客户端筛排从 Data 页拿掉后，有人会找右键筛选] → 表头输入框始终可见，替代该入口。

## Migration Plan

纯前端行为变更，无数据迁移、无 API 版本。随前端发布即可；回滚即回退表 Data SQL 生成与网格筛选行。已打开的表 tab 在刷新前仍是旧的无 `WHERE` 结果，下一次打开或刷新走新逻辑。

## Open Questions

无。逗号 `IN`、输入即查、SQL 结果页表头筛选若后续需要，另开 change。
