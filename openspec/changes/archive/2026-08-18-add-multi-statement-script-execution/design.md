## Context

当前执行链路每一层都是「一次一条」的形状：`SqlMonacoEditor.currentStatement()` 只取选区或光标所在语句；`SqlEditorPage.run()` 发送单个 `statement`；后端 `SqlExecutionService.execute()` 通过 `SqlStatementScanner.requireSingle` 强制单条，一次执行对应一个 `executionId`、一条历史记录、一个并发额度；响应 `SqlExecutionResult` 是单结果联合类型；`EditorTab` 的 `result`/`error`/`executionId` 都是单值；`ResultGrid` 只渲染一个结果。

有两条既有约束不可动摇。一是 `allowMultiQueries=false` 在 `backend-connection-security` 规格中是 non-overridable 的固定 JDBC 属性，`JdbcPropertyValidator` 会拒绝用户覆盖，因此不能靠驱动一次投递多条语句。二是 `autoCommit=true` 是执行契约的一部分，服务端不维护手动事务。

调研了主流实现（DBeaver `SQLScriptParser` + Alt+X 逐条 consecutively、CloudBeaver 的 Statistics 汇总页签 + 每条 Result 页签、Beekeeper Studio 的 `sql-query-identifier` + 解析失败退化为整段、phpMyAdmin/Adminer 服务端切分后顺序执行），结论一致：**没有产品依赖驱动的多语句开关，全部先切分再逐条顺序执行**。这与我们的安全基线天然吻合。

前端已具备切分能力：`web/src/sql-editor/sql.ts` 的 `splitSql` 是状态机实现，正确忽略单引号、双引号、反引号、`#`、`--`、块注释中的分号，与后端 `SqlStatementScanner.split` 规则一致。本次改动是把这份既有能力从「找光标所在语句 / 拦截批量」升级为「驱动脚本编排」。

## Goals / Non-Goals

**Goals:**

- 用户可以一次执行编辑器全部语句或选区内全部语句，无需逐条手工运行。
- 复用现有执行接口与安全基线，后端零代码改动。
- 每条语句的结果可独立查看，并提供整个脚本的执行汇总。
- 脚本执行可随时停止，已完成结果不丢失。
- 「运行选中」成为可见的一等入口，不再隐藏在 `title` 属性里。

**Non-Goals:**

- 不支持跨语句会话状态（`SET @var`、`CREATE TEMPORARY TABLE`、`USE`、会话变量）。
- 不支持脚本级事务或回滚，不引入手动 commit 模式。
- 不支持 `DELIMITER` 客户端命令，存储过程/触发器脚本仍不在验收范围（延续既有规格立场）。
- 不实现 DBeaver 的「每条语句并行执行到独立页签」模式，本次只做串行。
- 不引入脚本分组 ID 来归并执行历史。
- 不改动后端执行、取消、历史、导出的任何契约。

## Decisions

### 决策一：前端串行编排，后端零改动

前端切分文本后，对每条语句依次调用现有 `POST /api/v1/sql/executions`，每条生成独立 UUID。

考虑过的替代方案是新增后端脚本接口，在一次请求内串行执行 N 条并返回结果数组。放弃原因：需要重新定义整脚本超时与单条超时的关系、重做取消语义、控制可能极大的响应体（可能被迫引入流式或轮询）、为历史建立父子关系，改动面和风险都显著更大。

前端编排的额外收益是后端 `Single-statement execution validation` 这条 requirement 完全不需要修改，`MULTI_STATEMENT_NOT_SUPPORTED` 继续作为权威兜底存在，只在前端切分失败退化时才会被触发。既有的取消、超时、配额、导出语义全部原样复用：每条语句独立 `executionId` 反而让 `CsvExportService` 的按 ID 重放导出天然可用于脚本中的任意一条查询。

代价是 N 条语句产生 N 次 HTTP 往返，以及下面的会话状态问题。

### 决策二：显式放弃跨语句会话状态，而不是静默失败

后端每次 `execute()` 都执行 `targets.borrow(source)` 取连接、结束时 `targets.release(source, connection)` 归还，因此第二条语句可能拿到不同的物理连接。DBeaver 与 CloudBeaver 用一个连接跑完整脚本，会话状态天然延续；我们做不到。

关键判断是：静默出错比不支持更糟。`SET @x = 1; SELECT @x;` 会「成功执行」但第二条读到 `NULL`，用户很难意识到原因。因此把限制写成显式 requirement，并在前端切分后扫描脚本，检测到 `SET`（非 `SET` 开头的赋值语法除外）、`CREATE TEMPORARY TABLE`、`USE` 时在执行前给出明确警告，说明这些语句不会影响后续语句。

这个取舍与项目既有立场自洽：规格已经声明不支持 `DELIMITER` 与过程脚本，且 `autoCommit=true` 意味着本来就没有跨语句事务。若后续确认必须支持会话状态，需要另开 change 走后端脚本接口路线。

### 决策三：Navicat 式运行语义，保留 Cmd/Ctrl+Enter 为单条

按钮语义随选区变化：无选区时显示「运行」并执行全部语句；有选区时文案切换为「运行选中」并执行选区内全部语句。两者都是脚本语义。

考虑过 Beekeeper 式的「按钮带下拉菜单」和「保持按钮为单条语义、另加独立的运行全部按钮」。选择 Navicat 方案是因为用户明确偏好，且按钮文案随上下文变化本身就是最强的可发现性提示——它同时解决了「run selected 没有可见入口」这个问题。

`Cmd/Ctrl + Enter` 保留为「运行当前语句」，这是跨编辑器的肌肉记忆，也是本项目现有行为，改掉会造成回归。`Cmd/Ctrl + Shift + Enter` 从「运行全部（多条则拦截）」变为「运行脚本」，与按钮行为一致。

因此按钮无选区时的语义确实发生了破坏性变化（单条 → 全部）。这是本次唯一的破坏性交互变更，需要在发布说明中点出。

### 决策四：结果区用 Statistics 汇总 + 每条 Result 子页签

照抄 CloudBeaver 的信息结构：一个汇总页签展示每条语句的序号、类型、状态、耗时、返回或影响行数，以及失败语句的位置；每条产生结果集的语句一个 `Result N` 子页签，内部复用现有 `ResultGrid`，从而自动继承电子表格式选区、值面板、客户端排序筛选固定、CSV 导出等全部既有能力。

`EditorTab` 从单结果扩展为语句结果集合，形如 `statements: { index, sql, status, result, error }[]`，并保留一个当前查看索引。单条执行是这个模型的退化情形（集合长度为 1），因此单条路径与脚本路径共用同一套渲染，避免出现两套结果 UI。

考虑过「只展示最后一个结果集」（实现最省，但脚本中间的查询结果丢失，Beekeeper 用户为此提过 issue）和「执行日志列表点开才看结果」（多一次点击）。子页签方案信息密度和可发现性最好。

### 决策五：遇错即停，并说明不可回滚

某条语句失败后立即停止后续语句，保留已完成语句的结果，在汇总页签标注失败语句的序号与错误信息。

DBeaver 提供 `Stop + rollback` / `Stop + commit` / `Ignore` 三选项，但 `Stop + rollback` 依赖手动事务模式，我们在 `autoCommit=true` 下只能实现 `Stop + commit` 语义。因此 UI 必须明确说明「已执行的语句不会回滚」，否则用户会误以为停止等于撤销。

不做「继续执行并汇总所有错误」，因为脚本语句通常有顺序依赖，前一条建表失败后继续跑插入只会产生一连串噪音错误。

### 决策六：切分失败退化为整段单条，由后端裁决

`splitSql` 遇到未闭合引号等情况不会报错，而后端 `requireSingle` 对 `select 'x` 这类输入会抛错，两侧口径存在不一致。借鉴 Beekeeper 的 `safelyIdentify`：前端切分若产出可疑结果（例如检测到未闭合的引号或注释状态在文本结束时仍未回到 normal），就把整段文本当作单条语句发送，让后端给出权威错误。

这比前端自行拦截更好：前端切分器不是完整解析器，自行判定语法错误会误伤合法 SQL，而后端本来就有权威校验和安全的错误信息。

### 决策七：脚本执行占用单个并发额度

脚本串行执行期间整个页签视为一个运行中执行，页签级重复提交禁止规则不变。因为同一时刻只有一个 HTTP 执行在飞，后端 `max-concurrent-per-user: 3` 不会被触碰，前端「最多 3 个并行」的限制仍然按页签计算，用户可以在别的页签同时跑脚本。

「停止」需要两层动作：调用取消接口终止当前在飞语句，同时清空待执行队列阻止后续语句发起。

## Risks / Trade-offs

- [用户在脚本中写 `SET @var` 或临时表，期望跨语句生效] → 规格显式声明不支持；前端执行前扫描并警告；若确需支持则另开 change 走后端脚本接口。
- [长脚本产生大量执行历史记录，历史面板被单次脚本刷满] → 本次接受。观察实际使用后再评估是否引入脚本分组 ID 归并显示。
- [N 条语句 N 次往返，长脚本整体耗时高于单连接批量执行] → 串行是安全基线的必然结果；UI 提供实时进度（第 i / N 条）与随时停止，让等待可感知可中断。
- [遇错即停后数据处于中间状态且无法回滚] → UI 在汇总页签明确标注已成功执行的语句数量与失败位置，并说明不可回滚；不提供误导性的「撤销」入口。
- [「运行」按钮语义变化导致老用户误触发全量执行] → 按钮文案随选区切换本身即为提示；脚本执行前的确认策略在实现时按语句数量决定（多于一条时展示将要执行的语句数）。
- [大量结果子页签占用浏览器内存] → 结果行数仍受 `rowLimit` 与后端字节上限约束；对脚本执行设置语句数量上限（默认 200 条），超限时拒绝并提示拆分脚本。
- [前端切分与后端切分规则出现漂移] → 两侧规则已一致（同一状态机逻辑），前端不做语法裁决，可疑输入一律交后端；`web/src/sql-editor/sql.test.ts` 与 `SqlStatementScannerTest` 保持对等用例。
