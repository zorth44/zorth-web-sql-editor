# 执行流程

## 连续执行与授权

- 完整实施任务按依赖持续阅读、实现、验证、修复、自查和阶段提交；任务编号是内部清单，不在每个编号完成后等待“继续”。阶段汇报不构成验收或停止。
- 常规组件拆分、文件组织、范围内的实现选择和普通测试失败自行处理。环境缺失先检查并准备授权范围内的依赖、服务和配置；工具要求升级权限时走实际审批流程。
- 外部问题只阻塞依赖它的工作。记录受影响项、尝试、证据、所需输入，继续独立任务；仅在交付标准达到或全部剩余工作受外部依赖阻塞时结束实施。
- 实施授权包括本地阶段提交。按可审查的功能阶段提交，仅暂存本任务文件；不得提交凭证、个人环境配置和构建产物。推送、PR 按用户授权执行，不自行合并、发布或接入生产。
- 需要改变产品范围、接口契约、凭证政策或约定文件归属时，提出具体决策问题并继续独立工作。已获授权的调整按授权范围执行。

## 工作区与变更记录

- 开始或恢复工作先检查 git 状态和用户改动，不覆盖无关工作。使用 worktree 时只编辑本任务的 worktree，不编辑其他工作区；搜索排除 `.worktrees/`，避免混淆分支代码。
- 不自行启动额外 Agent。并行工作如获授权，应先约定文件归属和共享契约；不同工作区服务使用独立端口，不共享破坏性测试 schema，不终止不属于本任务的进程。
- 功能实施采用 OpenSpec 时，先建立 change 并将范围映射为 tasks；`tasks.md` 是该 change 完成状态的唯一清单。`execution.md` 记录当前阶段、最近提交、测试命令及结果、下一步和阻塞，方案文档不重复维护完成勾选。
- 每个功能阶段更新执行记录。恢复时先读本路由入口、相关子系统文档、本 change 的 tasks/execution 和 git 状态，继续未完成工作，不重做已验收步骤。
- 已归档 change 用于历史回溯；维护工作读取当前 `openspec/specs/`，不沿用旧分支分工或失效的运行会话。

## 验证与交付

- 验证要求见[代码标准](code-standards.md)，专项场景见对应[子系统入口](subsystems/README.md)。不得删除测试、放宽断言、跳过门禁或降低权限保护来制造通过；既有失败与本次回归分别记录。
- Mock/Stub、本地真实数据库、真实 Agent 联调和生产验收分别报告，不能相互替代。失败与跳过如实记录；历史通过结果不代表当前环境仍通过。
- 交付包含运行方式或页面预览、变更说明、实际测试结果（含失败和跳过）、提交记录、已知问题与外部依赖。纯文档变更检查内容、相对链接、过期引用和 diff，无代码改动时不要求运行应用全套测试。
- 用户可显式启用持续 Goal；完成以证据为准，目标范围之外的真实联调或生产验收须单列待办，不标成整体完成。
